## 高优先级

### 1. 从审核队列打开详情时 `task.columns` 未定义，会导致前端崩溃

- 严重度：High
- 位置：`backend/api/db_operations.py` `_task_to_dict`、`frontend/src/components/database/ReviewDialog.tsx`（`task.columns.map`）
- 问题：
  - 后端 `_task_to_dict` / `GET /api/db_operations/review/{id}` 返回的是 `preview_columns` 和 `preview_rows`，并不包含 `columns`。
  - `ReviewDialog` 渲染影响数据预览时使用的是 `task.columns.map(...)`。
  - 新建审核后立即打开时，`DatabasePanel` 把 `previewOperation` 的结果（含 `columns`）和 `submitReview` 结果合并，所以正常。
  - 但从新的 `ReviewQueue` 通过 `getReview()` 打开已有任务时，`task.columns` 为 `undefined`；只要该任务有 `preview_rows`（如 DELETE / UPDATE 影响行数大于 0），就会触发 `undefined.map`，导致页面崩溃。
  - 同时 `has_backup`、`safety_message` 也缺失，队列打开的详情里备份状态和风险提示显示不正确。
- 建议：
  - 在 `_task_to_dict` 中返回 `columns`（取 `preview_columns`），并补上 `has_backup`、`safety_message` 或由前端按 `preview_columns` / `backup_id` 推导。
  - 或让 `ReviewDialog` 统一使用 `task.preview_columns ?? task.columns`，并对缺失字段做防御。

## 中优先级

### 2. 审核队列读取接口未限制角色

- 严重度：Medium
- 位置：`backend/api/db_operations.py` `list_reviews`、`get_review`
- 问题：`GET /api/db_operations/reviews` 和 `GET /api/db_operations/review/{id}` 只使用 `get_current_user`，任何已登录用户（包括 `viewer`）都能通过 API 读取所有待审批任务的 SQL 文本和影响数据预览。前端虽然只对 approver / admin 显示“审核队列”入口，但 API 层没有同等权限校验。
- 影响：只读角色可越权读取写操作 SQL 与预览数据。
- 建议：将这两个只读接口限制为 `require_roles("approver")`（或至少 `operator/approver`），并考虑按提交人 / 角色过滤列表。

## 低优先级

### 3. `approved_by` 字段语义不一致

- 严重度：Low
- 位置：`backend/api/db_operations.py` `approve_review`
- 问题：待第二审批阶段，`approved_by` 保存第一审批人；任务完成后又被覆盖为第二审批人。虽然新增的 `first_approver_id` / `second_approver_id` 已保留完整信息，但 `approved_by` 容易造成误读。
- 建议：统一为“最终执行审批人”，或前端展示改为使用 `first_approver_id` / `second_approver_id`。

### 4. `_record_approval` 在写操作执行之后调用

- 严重度：Low
- 位置：`backend/api/db_operations.py` `approve_review`
- 问题：审批记录 `_record_approval` 在 `conn.execute(task["sql"])` 之后才写入；若该记录写入失败，业务写操作已执行但审批元数据可能缺失，状态与审计不一致。
- 建议：审批元数据与状态更新尽量先持久化，再执行写操作；对不可避免的顺序增加失败补偿。

### 5. 表清单仍每次请求全量读取

- 严重度：Low
- 位置：`backend/api/db_operations.py` `_require_table`、`_quote_table_if_known`
- 问题：遗留项，未修复。表数据 / 结构请求每次调用 `get_tables()`，大库下有额外元数据开销。
- 建议：缓存表清单或按需校验。

### 6. PII 脱敏正则可能误伤普通数据

- 严重度：Low
- 位置：`backend/utils/masking.py`
- 问题：遗留项，未修复。11 位数字可能被当作手机号、长数字串可能被当作银行卡号，自由文本中也可能误掩码。
- 建议：结合列名上下文收紧策略，支持脱敏开关与例外列。
