# Bugbot 代码审查报告（第五轮）

审查范围：当前工作区未提交改动（新增 CI/CD、Docker、LLM Provider 抽象与韧性、用量计量、上下文管理、前端自动化测试、审计哈希链、回滚受控等）。

结论：发现 2 个中优先级问题、1 个低优先级问题。既有历史问题（审核弹窗关闭、字段不一致等）已修复。

## 中优先级

### 1. 流式请求对所有 Provider 无条件发送 `stream_options`

- 严重度：Medium
- 位置：`backend/llm/openai_impl.py` `chat_stream`
- 问题：`chat_stream` 固定发送 `stream_options: {"include_usage": True}`，但 `factory.py` 现已支持 OpenAI / DeepSeek / 智谱 / 月之暗面 / 通义千问 / Groq / Ollama 等多个 Provider。部分 OpenAI 兼容服务（尤其 Ollama，部分老版本第三方网关）不支持该字段，可能直接 400 或忽略 usage，导致流式调用失败。
- 影响：新增的“多 Provider”能力在部分 Provider 上可能不可用。
- 建议：按 Provider 开关 `stream_options`，或不支持时降级为普通流式并在最后估算 usage；增加各 Provider 的连接测试覆盖流式路径。

### 2. LLM 客户端存在重复重试，且 timeout 类型需验证

- 严重度：Medium
- 位置：`backend/llm/openai_impl.py` `OpenAILLM.__init__`、`_create_completion`
- 问题：
  - `AsyncOpenAI` 默认自带 `max_retries=2`，同时代码又手动实现 `_create_completion` 重试循环，二者叠加会导致同一请求被多次重复发送，放大成本与延迟。
  - `timeout=self.timeout` 传入的是 `httpx.Timeout` 对象，而 OpenAI SDK 对 `timeout` 参数类型要求需与当前 SDK 版本核对，类型不匹配可能导致请求异常。
- 影响：重试次数和成本不可控，存在潜在运行时兼容风险。
- 建议：实例化客户端时显式传 `max_retries=0`，只保留手动重试；验证 `timeout` 参数类型，必要时改用 `float` 秒或 SDK 的 `Timeout` 类型。

## 低优先级

### 3. LLM 用量计量不完整

- 严重度：Low
- 位置：`backend/agent/react_loop.py`、`backend/agent/classifier.py`、`backend/api/chat.py`
- 问题：
  - 意图分类使用非流式 `llm.chat()`，其 usage 未落库。
  - ReAct 达到最大迭代后的最终总结调用中，`usage` 事件被忽略，未计入用量。
  - 发生 fallback 模型时，`chat.py` 用 `app_settings.llm_model` 作为 model，未记录实际使用的 fallback 模型。
- 影响：用量 / 成本统计偏低，且 fallback 场景下归因不准确。
- 建议：统一在 LLM 客户端层记录 usage 与真实 model，避免在各调用点重复采集；非流式路径同样落库。
