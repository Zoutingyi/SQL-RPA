## Findings

### P1 — C-01 缺少真正的租户模型与隔离

> **整改状态：后端已完成（2026-08-22）**  已增加 Tenant、Membership 与租户级 RBAC；会话、消息、文档、记忆、向量、审核、备份、审计、通知、用量、配额和账单等核心实体及查询均强制绑定 `tenant_id`，用户资源同时绑定 `owner_id`。目标业务库配置使用版本化密钥加密，并按租户建立独立连接和缓存；后台 saga 修复、审批过期处理也恢复所属租户上下文。跨租户核心资源及目标库物理隔离测试：`test_core_resources_are_tenant_scoped`、`test_tenant_target_databases_are_isolated`；全量回归 `191 passed, 3 skipped`。

> **补充整改：后端已完成（2026-08-23）**  `POST /api/auth/login` 现在返回顶层及 `user.tenant_id`：优先选择用户可访问的默认租户，否则选择首个有效 Membership；同时返回 `tenants` 列表及租户内角色，首次登录不再要求用户预先获知租户 UUID。生产 Compose 默认设置 `MULTI_TENANT_ENABLED=true`，并在 `.env.example` 明确单租户/多租户配置。验收测试：`test_login_returns_first_accessible_tenant`；全量回归 `192 passed, 3 skipped`。

> **补充整改：后端已完成（2026-08-24）**  数据库状态、重连、表列表、Schema 和表数据接口已强制认证并使用显式租户上下文；多租户请求缺少 `X-Tenant-ID` 时拒绝，重连仅关闭当前租户连接，全局 API Key 无法进入。Agent 文档列表、详情、向量及 FTS 检索均绑定租户。租户管理员只能通过 Membership 接口调整租户内角色，多租户模式禁止其修改全局 User 角色、密码或状态。发票、明细、支付、查询及幂等竞争均包含 `tenant_id`，支持不同租户复用同一客户端幂等键。新增 4 组跨租户/并发测试；全量回归 `196 passed, 3 skipped`。

> **✅ 前端已完成（2026-08-23）**  已接入登录租户上下文、租户切换、成员角色管理、无权限状态、租户用量/配额/账单；API、聊天流和 SSE 请求统一携带 `X-Tenant-ID`，租户切换会清空租户作用域缓存。前端 lint、15 项测试和生产构建通过。当前后端登录响应未返回 `tenant_id`，前端暂以登录页租户 ID 输入完成首次上下文引导，建议后端返回默认/首个可访问租户以改善首次登录体验。

- 位置：`backend/models/schemas.py:154`
- 配额、用量、发票和用户仍只按 `user_id` 关联。
- 没有 Tenant、Membership 模型，也没有在会话、文档、数据库连接、审核、备份、用量、账单、通知等对象上设置 `tenant_id`。
- 因此无法强制执行租户边界、租户 RBAC、租户配额或租户账单聚合；SaaS/多租户交付下 C-01 尚未实现。

### P1 — 会话存在跨用户读取与写入风险

> **整改状态：后端已完成（2026-08-22）**  Conversation 增加不可为空的 `owner_id`；会话列表、消息读取、改名、删除及 `/api/chat` 追加消息均同时校验资源 ID 和当前用户 owner。跨用户读取/写入/改名/删除均返回 404，负向测试：`test_conversation_owner_is_enforced`。

- 位置：`backend/api/chat.py:51`
- 已认证调用者可以提交任意 `conversation_id`；处理器只按 ID 加载会话并追加消息。
- `Conversation` 没有 owner/tenant 字段，也没有校验当前用户是否有权访问。
- 获得其他会话 UUID 的用户可能通过 Agent 上下文间接读取历史，并向该会话写入消息。

### P1 — 账单生成和支付幂等存在并发竞争

> **整改状态：后端已完成（2026-08-22）**  发票增加数据库唯一 `invoice_key`，支付继续以唯一幂等键作为并发同步点；唯一键竞争时回读已提交记录，不再返回 500。并发验收测试：`test_concurrent_invoice_and_payment_are_idempotent`。

- 位置：`backend/api/billing.py:42`
- 发票创建使用“先查询、后插入”，但 `(user_id, period_start, period_end)` 没有数据库唯一约束或锁。
- 并发请求可能为同一用户和周期创建并收费两次。
- 支付幂等也存在相同竞争：两个并发请求可能同时查不到记录，其中一个最终产生未处理的 `IntegrityError/500`，而不是返回已有支付。

### P1 — 配额不是并发场景下的硬限制

> **整改状态：后端已完成（2026-08-22）**  模型调用前在内部库事务中锁定配额并原子预留 token/成本额度；并发请求将活动预留计入余额，超额请求返回 429。流正常结束、异常或客户端断开均在生成器 `finally` 中持久化计量记录并结算预留，超时预留自动回收。并发测试：`test_quota_uses_atomic_reservation`。

- 位置：`backend/api/usage.py:124`
- 配额检查只统计聊天开始前已经持久化的用量。
- 用量在流式请求结束后才写入；多个并发聊天可以同时通过相同额度检查并显著超额。
- 失败或断开的流式请求也可能逃避持久化计量，因此不能作为 C-01/P1 的硬配额验收。

### P1 — Approver 可绕过 Admin 用量权限边界

> **整改状态：后端已完成（2026-08-22）**  `/api/usage/overview` 改为仅允许 admin，不再通过内部路由调用绕过依赖。负向测试确认 approver 返回 403：`test_approver_cannot_read_global_usage`。

- 位置：`backend/api/usage.py:107`
- `/api/usage/overview` 允许 `approver`，随后直接调用 `usage_by_user(days, user)`。
- Python 内部直接调用不会执行 FastAPI 的 admin-only 依赖。
- 结果是 approver 可以获取全部用户的用量和配额数据。

### P2 — 多 worker 可能重复发送通知

> **整改状态：后端已完成（2026-08-22）**  投递前使用条件 UPDATE 原子抢占为 `sending`，记录租约时间并回收超时租约；只有抢占成功的 worker 执行外部 POST。并发测试确认两个 worker 仅发送一次：`test_notification_delivery_has_single_atomic_claim`。

- 位置：`backend/notifications.py:38`
- `deliver_pending` 查询待发送记录后直接执行外部 POST，没有原子抢占、租约或 `FOR UPDATE SKIP LOCKED`。
- 每个应用 worker 都会启动投递循环，多 worker 可同时选择并发送同一通知，造成重复邮件、IM 或 Webhook，以及错误的 attempts/status。

## 测试缺口

现有新增测试主要覆盖正常路径和顺序支付幂等，没有覆盖：

- 租户隔离和跨用户会话访问
- 并发配额准入
- 并发发票和支付创建
- 用量 overview 的角色权限边界
- 多 worker 通知抢占

## 验收建议

在上述 5 项 P1 修复并补齐相应并发、越权和租户隔离测试前，不应将 C-01 或相关 P1 整改标记为完成。P2 通知投递也需要数据库级原子抢占后再验收。
