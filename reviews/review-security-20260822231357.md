# Security Review Report

- 审查时间：2026-08-22 23:13:57（Asia/Shanghai）
- 审查范围：当前分支相对默认基线的全部变更
- 审查重点：后端声称完成的 C-01、P1、P2 安全整改
- 审查结论：发现 7 项问题，其中 P1 3 项、P2 4 项；C-01 及相关 P1/P2 安全整改不能验收为完成。

## Findings

### P1 — 缺少租户及资源所有者隔离

> **整改状态：后端已完成（2026-08-22）**  已落地 Tenant、Membership、租户级角色和请求租户上下文；Conversation、Message、Document、UserMemory、DbReviewTask、DbBackup、审计及其他核心业务对象均包含不可为空的 `tenant_id`，用户私有资源包含 `owner_id`，路由、服务、向量检索、唯一约束与后台补偿均按租户过滤。租户目标数据库凭据加密保存并建立独立连接，禁止共享全局连接。负向测试覆盖跨租户资源访问和目标库隔离：`test_core_resources_are_tenant_scoped`、`test_tenant_target_databases_are_isolated`；全量回归 `191 passed, 3 skipped`。

> **补充整改：后端已完成（2026-08-23）**  登录成功后由后端从有效 Tenant/Membership 中选择默认或首个可访问租户，并在响应顶层、用户对象及租户列表中返回 `tenant_id`/租户角色；无有效 Membership 的多租户用户拒绝登录。生产 Compose 默认启用 `MULTI_TENANT_ENABLED=true`。验收测试：`test_login_returns_first_accessible_tenant`；全量回归 `192 passed, 3 skipped`。

> **补充整改：后端已完成（2026-08-24）**  数据库浏览全接口强制用户/显式租户并拒绝多租户默认回落及全局 API Key；Agent 文档元数据、向量检索和关键词 FTS 均按租户隔离；租户管理员只可改变 Membership.role，无法经用户接口修改全局身份凭据或状态；账单所有读取、并发唯一点及幂等键均加入租户范围。负向测试覆盖跨租户目标库、文档工具/检索、双租户成员角色以及跨租户同幂等键；全量回归 `196 passed, 3 skipped`。

> **✅ 前端已完成（2026-08-23）**  已接入登录租户上下文、租户切换、成员角色管理、无权限状态、租户用量/配额/账单；API、聊天流和 SSE 请求统一携带 `X-Tenant-ID`，租户切换会清空租户作用域缓存，前端不承担或声明数据隔离。前端 lint、15 项测试和生产构建通过。当前后端登录响应未返回 `tenant_id`，前端暂以登录页租户 ID 输入完成首次上下文引导，建议后端返回默认/首个可访问租户以避免首次登录上下文歧义。

- 位置：`backend/models/schemas.py:64`、`backend/api/conversations.py:22`
- Conversation、Message、Document、UserMemory、DbReviewTask、DbBackup 和审计记录缺少 `tenant_id` 或所有者范围。
- 会话接口仅凭客户端提供的 ID 查询、修改和删除，没有绑定当前用户或租户。
- 任意已认证 viewer 可能枚举、读取、改名或删除其他用户的会话；文档、记忆、审核任务和备份也存在类似全局共享风险。
- 建议：增加 Tenant、Membership、不可为空的 `tenant_id` 及必要的 `owner_id`；所有查询、关联和唯一约束必须包含租户；补充跨租户及跨用户负向测试。

### P1 — 通知事件可能跨租户泄露

> **整改状态：后端已完成（2026-08-22）**  Notification、Endpoint、Delivery、Preference 均增加 `tenant_id`；发布事件只选择同租户端点，站内查询、未读数、端点 CRUD、偏好与测试发送均绑定当前租户。跨租户测试确认租户 A 事件不会生成租户 B 投递：`test_notification_events_are_tenant_scoped`。

- 位置：`backend/notifications.py:15`
- 通知分发选择所有启用的 NotificationEndpoint，并把领域事件投递给全部端点。
- 端点、事件和投递记录没有租户或接收人归属，多租户部署时租户 A 的审核内容可能发送到租户 B 的 Webhook。
- 建议：为端点、事件、投递增加 `tenant_id` 和可选 `recipient_id`，事件产生时写明接收范围，分发时强制按租户、事件类型和接收人过滤。

### P1 — 审批工作流授权未闭环

> **整改状态：后端已完成（2026-08-22）**  审核任务创建、列表、详情、事件、执行结果及状态原子更新均绑定当前 `tenant_id`；operator 不再能过期/升级/转派，转派目标必须是同租户有效 approver/admin，指定处理人后其他审批员不得批准或拒绝。跨租户和跨角色负向测试：`test_review_tenant_and_assignment_authorization`。

- 位置：`backend/api/db_operations.py:994`
- operator 可对任意活动任务执行过期、升级或转派；批准、拒绝、列表和详情没有租户范围，也未强制校验 `assigned_to`。
- 攻击者可能干扰其他用户或租户的审批队列，将任务转给自己、拒绝任务，或执行指定审批人才能执行的操作。
- 建议：定义操作权限矩阵；查询和原子状态更新同时绑定 `tenant_id`、`assigned_to`、当前状态及版本号；补充跨租户、非指定审批人和状态竞争负向测试。

### P2 — Webhook 存在 DNS rebinding SSRF

> **整改状态：后端已完成（2026-08-22）**  每次投递和测试发送前重新解析，拒绝任一非公网地址、userinfo、非 HTTP(S) 及非允许端口；连接固定到本次校验的 IP，保留 Host/SNI，且禁止重定向。负向测试：`test_ssrf_rejects_private_or_mixed_dns`。

- 位置：`backend/notifications.py:45`
- Webhook 地址只在配置时验证；投递时域名重新解析但没有再次验证或固定目标 IP。
- 攻击者可让域名先解析至公网地址通过检查，再绑定到 loopback、私网、链路本地或云元数据地址。
- 建议：每次投递前解析并拒绝所有非公网地址；连接至固定的已验证 IP并保留 hostname 用于 TLS；禁止重定向或逐跳校验；限制协议、端口、响应大小和超时。

### P2 — 并发请求可绕过配额

> **整改状态：后端已完成（2026-08-22）**  新增数据库原子额度预留/结算模型；调用前锁定配额并统计活动预留，流结束、异常和断开统一在 `finally` 结算，过期租约可回收。并发负向测试确认 100 token 配额下两个 60-token 预留仅一个获准：`test_quota_uses_atomic_reservation`。

- 位置：`backend/api/usage.py:124`、`backend/api/chat.py:152`
- 配额采用“读取历史用量→允许请求→流结束后记账”，并发请求会读取相同旧余额并全部通过。
- 流式请求中断或异常也可能造成少记账。
- 建议：模型调用前原子预留额度，结束后按实际用量结算并释放余额；异常、超时和中断都必须结算；增加高并发和预留过期回收测试。

### P2 — 全局 API Key 可绕过租户隔离

> **整改状态：后端已完成（2026-08-22）**  新增显式 `MULTI_TENANT_ENABLED` 模式；启用时旧全局 API Key 被拒绝为 401，机器身份不能再以无租户 admin 进入。JWT 请求必须通过 `X-Tenant-ID` 对应的有效 Membership。负向测试：`test_global_api_key_disabled_in_multitenant_mode`。

- 位置：`backend/auth.py:170`
- 旧版全局 API Key 被映射为无限制 admin，没有租户、scope、有效期、独立撤销或真实操作者身份。
- 密钥泄露会影响所有租户并破坏审计归责。
- 建议：多租户生产环境移除全局 API Key；机器访问改为绑定租户、角色/scope、有效期及可独立撤销的 service account 凭据。

### P2 — Approver 可越权读取全局用量和费用

> **整改状态：后端已完成（2026-08-22）**  全局 overview 仅允许平台 admin，approver 不再能通过路由函数内部调用绕过权限。负向测试确认返回 403：`test_approver_cannot_read_global_usage`。

- 位置：`backend/api/usage.py:106`
- `/api/usage/overview` 对 approver 开放，但通过直接调用路由函数绕过了 `usage_by_user` 的 admin 依赖。
- 审批员可以获取所有用户标识、用量、费用和配额，多租户下构成跨租户数据泄露。
- 建议：全局 overview 仅允许平台管理员；其他角色只返回本人或当前租户的脱敏聚合；将共享查询移入服务层并在服务层强制权限及租户条件。

## 安全验收建议

1. 先完成 Tenant/Membership 与全业务实体租户迁移，禁止路由按裸 ID 访问资源。
2. 修复会话、文档、记忆、审核、备份、审计、通知和用量接口的跨租户授权。
3. 修复通知端点隔离及 Webhook DNS rebinding SSRF。
4. 配额改为原子预留/结算；全局 API Key 限制为明确的单租户兼容模式。
5. 补充跨租户、跨用户、非指定审批人、并发配额和 SSRF 负向测试。

在上述 P1 问题解决前，不应将 C-01 或相关安全整改标为完成。
