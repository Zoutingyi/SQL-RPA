# SQL 参数化改造立项说明

> ⚠️ 【单独立项 · 高优先级 · 底层改造】  
> 来源：Security Review Medium #2  
> 状态：不纳入当前安全加固批次，单独排期、单独评审

## 一、立项背景

当前 SQL 执行链路仍以“原始 SQL 字符串”直接交给数据库连接器执行，安全防护依赖关键字正则、多语句检测和 WHERE 黑名单。安全审查判定为 Medium；前端团队评估认为引入 sqlglot / AST 白名单做参数化属于较大底层改造，不适合在安全加固中顺手完成，因此单独立项。

## 二、问题与风险

- 提示注入或 LLM 生成异常 SQL 时，签名式正则存在绕过空间。
- 写操作虽然有人工审批兜底，但审批人误批后仍可能执行越权 SQL。
- 现有正则难以覆盖 SQLite / MySQL 的方言差异和语法变体。
- 多语句、注释、UNION / 子查询等复杂形态的拦截一致性不足。

## 三、改造目标

1. 由“执行原始 SQL 字符串”演进为“参数化 SQL + 参数列表”。
2. 引入 sqlglot 对 SQL 做 AST 解析和结构化白名单校验。
3. 兼容 SQLite、MySQL，并为后续 PostgreSQL 预留扩展点。
4. 保留现有的人工审核与备份回滚机制，不降低安全兜底能力。

## 四、技术方案

### 1. LLM 输出约束

- 更新系统提示词，要求模型输出 `sql` 和 `params` 两个字段。
- 扩展工具 JSON Schema，增加 `params` 参数。
- 对参数缺失或非法的工具调用采用 fail-closed 处理。

### 2. SQL 解析与校验

- 使用 sqlglot 解析 SQL，校验单语句、操作类型（SELECT / INSERT / UPDATE / DELETE）。
- 禁止 DDL、多语句、注释注入和危险函数。
- 对表名 / 列名做白名单校验，并从 AST 提取标识符。

### 3. 执行层改造

- `query_db` / `execute_sql` / 审核执行统一走参数绑定。
- 复用连接器已有的 `query(sql, params)`、`execute(sql, params)`、`execute_many`。
- 保留 SQLite `?` 与 MySQL `%s` 方言占位符适配。

### 4. 审核与回滚联动

- 审核任务同时保存 SQL 与参数，审核界面展示可读的最终 SQL。
- 批准执行时使用参数化执行；备份 / 回滚继续沿用事务化快照。

## 五、范围边界

### 纳入范围

- SELECT 只读查询的参数化与 AST 白名单。
- INSERT / UPDATE / DELETE 的参数化与 AST 白名单。
- SQLite、MySQL 双方言适配。
- 与审核队列、备份回滚、Agent 工具链路的全链路改造。

### 不纳入范围

- PostgreSQL 支持（仅预留扩展点）。
- DDL / 结构变更能力。
- 完全移除人工审核机制。
- 动态数据权限 / 行级安全策略。

## 六、建议里程碑

| 阶段 | 内容 |
| --- | --- |
| M1 | 方案评审与 sqlglot 兼容性验证 |
| M2 | LLM prompt / 工具 schema 参数化改造 |
| M3 | AST 白名单与危险 SQL 拦截实现 |
| M4 | 连接器参数化执行、审核与回滚联动 |
| M5 | 安全对抗测试、全量回归与灰度 |

## 七、验收标准

- 危险 SQL 及其方言变体均被 AST 层拦截。
- SELECT / 写操作均以参数化方式执行，不直接拼接用户或模型字符串。
- 现有后端测试全部通过，并新增安全对抗测试用例。
- SQLite 与 MySQL 均完成集成验证。
- 人工审核与备份回滚功能不回归。

## 八、风险与依赖

- sqlglot 版本与 Python 版本兼容性需提前验证。
- LLM 输出 `sql + params` 的稳定性需要 schema 约束、重试和降级策略。
- SQL 字符串执行调用面较广，需全链路回归，避免遗漏。
- MySQL 方言的 AST 差异需专项覆盖。

## 九、优先级标记

- 建议优先级：**P1（交付前完成）**。
- 实施方式：**单独立项、单独排期**，不与当前安全加固批次合并。
