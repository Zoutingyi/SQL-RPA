# 用户整改——前端技术栈清单

最后更新：2026-08-25  
对应计划：[用户整改-前端整改计划.md](用户整改-前端整改计划.md)  
适用目录：`frontend/`

文档状态：**V1.0 商业交付技术基线**。本清单同时区分“当前已安装”和“本期必须引入”，
避免开发人员把建议版本误认为项目已具备的能力。

## 一、技术选型原则

- 优先复用项目现有 React、React Router、Zustand、统一 API client 和组织上下文能力。
- 用户账号资料与部门任职模型分层，避免继续把部门角色当作全局用户属性。
- 前端只做交互约束和及时反馈；身份、权限、隔离、密码安全和审计以后端为最终边界。
- 密码、令牌和完整个人信息不进入持久化业务状态、日志、遥测或 URL。
- 仅为复杂表单、契约校验和 E2E 增加必要依赖，控制包体积和维护面。

## 三、本期必须新增并锁定的依赖

### 3.1 表单与运行时契约

- React Hook Form `7.x`：管理新增用户和修改密码表单，减少敏感输入的无关重渲染，
  支持字段错误、焦点管理和提交锁。
- Zod `4.x`：定义用户名、电话、密码和 API DTO 的运行时 schema。
- `@hookform/resolvers` `5.x`：连接 React Hook Form 与 Zod。

使用约束：

- schema 必须跟随后端已确认规则，前端不得私自制定比后端更宽松的安全规则。
- API 响应解析失败视为契约错误，不得用 viewer、admin、空部门等危险默认值继续运行。
- 密码表单不注册到全局 Zustand，也不保存到浏览器存储。

### 3.2 测试与质量

- Playwright `1.x`：首次登录强制改密、平台管理员无部门访问边界、多任职切换和并发重复
  提交的 E2E 测试。
- `@vitest/coverage-v8`：生成语句和分支覆盖率报告并实施阈值门禁。
- `@axe-core/playwright`：用户创建、个人设置和强制改密页面的自动化可访问性检查。

引入时锁定经项目验证的具体版本，并提交 lockfile；本清单只规定兼容主版本，不用文档
替代依赖锁定。

执行约束：

- 依赖合并前必须记录实际锁定版本、用途、许可证、gzip 增量和安全扫描结果。
- React Hook Form、Zod、resolvers、Playwright、coverage 和 axe 未进入 `package.json`、lockfile
  与 CI 前，对应任务不得标记完成。
- 不允许同时引入第二套表单、schema、路由、状态或 HTTP 客户端框架。

## 四、功能与技术栈对应关系

### 4.1 用户与任职类型

- TypeScript discriminated union 表达 `platform`、`department` 和 `password_change_required`
  会话状态。
- Zod schema 验证登录、`/api/auth/me`、用户列表、用户创建和改密响应。
- 现有 `src/types/organization.ts` 继续承载组织树和 membership 基础模型；用户专属字段放入
  `src/types/user.ts`，避免循环依赖。

建议核心模型：

```ts
type PermissionState =
  | { status: "unassigned"; role: null }
  | { status: "assigned"; role: "viewer" | "operator" | "approver" | "admin" };

interface UserProfile {
  id: string;
  username: string;
  display_name: string | null;
  phone: string | null;
  is_active: boolean;
  is_platform_admin: boolean;
  must_change_password: boolean;
  password_changed_at: string | null;
}

interface UserMembership {
  id: string;
  organization_id: string;
  organization_path: string[];
  organization_level: "company" | "department" | "group" | "individual";
  job_title: string | null;
  is_primary: boolean;
  active: boolean;
  permission_state: PermissionState;
}

type AuthPhase =
  | "anonymous"
  | "restoring"
  | "password_change_required"
  | "platform"
  | "department"
  | "unavailable";
```

实现字段名以后端发布的 `user-api-v1` OpenAPI 为准。

商业交付时不再保留“最终字段名待确认”：UFE-00 完成后，生成 DTO、Zod schema、OpenAPI
快照和本节示例必须一致。`organization`、`current_membership` 对无部门平台管理员使用明确
`null`；字段缺失属于契约错误。

### 4.2 登录与路由守卫

- React Router 嵌套路由分别承载认证守卫、强制改密守卫、平台权限守卫和部门上下文守卫。
- Zustand `authStore` 保存非敏感身份摘要；`organizationStore` 只在允许初始化部门上下文时运行。
- `/api/auth/me` 是刷新后恢复身份的唯一事实来源，不用用户名、旧 localStorage 角色或页面
  路径推断平台管理员。
- `Navigate` 只负责用户体验；后端 401/403 是最终安全响应。
- 守卫顺序固定为：认证恢复 → 强制改密 → 平台/部门域 → membership/角色 → 页面；每一层
  都有 loading、allowed 和 denied 三种明确状态，禁止在恢复期间短暂渲染业务页面。

### 4.3 管理员新增用户

- React Hook Form 管理 7 个字段和提交状态。
- Zod `transform`/`refine` 执行 trim、字符规则、电话格式、密码一致性和权限空值建模。
- 组织选择器复用 `organizationStore.tree`，使用节点 ID 提交，不提交展示路径作为身份依据。
- `crypto.randomUUID()` 生成幂等键；键只保存在组件提交会话内，不包含用户名或电话。
- 统一 API client 注入 `Idempotency-Key`，AbortController 处理离开页面或查询更新。

### 4.4 用户列表与编辑

- 服务端分页、搜索和筛选；前端保留当前查询参数，过期请求通过 AbortController 取消。
- 账号资料更新与 membership 更新使用不同 API 模块和 DTO。
- 电话显示由纯函数统一脱敏；若后端已经脱敏，前端不得尝试还原。
- 409 或版本冲突通过统一错误适配器触发详情刷新，不在旧对象上继续覆盖。

### 4.5 个人设置与修改密码

- `/profile` 使用路由级 `lazy` 拆包，可直接访问和刷新。
- 资料展示使用语义化只读内容，不使用 disabled 输入框伪装可编辑表单。
- 修改密码表单状态限制在组件内；输入采用 `current-password` 和 `new-password` 自动完成语义。
- 改密后由 authStore 原子替换令牌或执行完整登出，随后清理 organization scope。

### 4.6 用户菜单

- React 本地状态控制弹出菜单，React Router `Link`/`navigate` 进入个人设置。
- WAI-ARIA menu/button 语义或同等可访问的 disclosure 模式处理焦点、Escape 和点击外部关闭。
- 展示名统一由 `getUserDisplayName(user)` 计算，避免各页面出现不同回退规则。

## 六、API client 技术要求

- 认证令牌沿用统一注入机制；禁止在组件中手工拼接 Authorization。
- 部门业务请求携带当前后端规定的组织和 membership 上下文；平台 API 明确声明不携带
  部门上下文，不能因缺省而自动变成全组织访问。
- 用户创建支持自定义 `Idempotency-Key` 头，并允许安全重试复用同一个键。
- 创建接口严格识别 201、幂等重放 200 与 409 摘要冲突；自动重试仅限网络错误和明确可重试
  5xx，且保持原键，422/403/409 不自动重试。
- 请求错误统一规范为包含 `status`、`code`、`field_errors`、`request_id` 的前端错误类型。
- 401 清理认证和组织状态；403 刷新权限；409 刷新资源；422 映射字段错误；429 展示
  冷却提示；5xx 允许用户用原幂等键重试创建请求。
- 请求体、响应体和 Header 的调试日志必须经过敏感字段清洗。
- API 响应在进入 Store 前通过 Zod 校验；失败转换为 `CONTRACT_MISMATCH`，记录 request ID 和
  schema 版本，不记录原始响应正文。
- 用户管理 V1 开启时，404/405 视为部署不一致并阻断页面，不得回退旧 `/api/tenants` 或旧
  全局 `User.role` 逻辑。

## 七、状态管理技术要求

`authStore` 可保存：

- 当前用户的非敏感资料摘要。
- 平台管理员与强制改密标记。
- 当前认证阶段、初始化状态和不含密码的错误状态。
- 访问令牌（延续当前架构；后续如后端支持 HttpOnly Cookie，应迁移并删除 JS 令牌存储）。

令牌存储商业化约束：当前 Bearer/localStorage 架构属于已知 XSS 风险。本期若不迁移
HttpOnly + Secure + SameSite Cookie，必须由 Security Review 明确接受风险，并同时满足严格
CSP、无未审计第三方脚本、令牌不进入日志/遥测、短有效期和改密/停用全量撤销；否则阻断发布。

`organizationStore` 可保存：

- 后端返回的有效任职和组织树。
- 当前组织、membership、权限摘要及 context revision。
- 部门切换过程、兼容模式和不含个人敏感信息的错误。

禁止保存：

- 当前密码、新密码、确认密码、默认密码或密码哈希。
- 完整用户创建请求。
- 可长期复用的初始密码提示。
- 未经后端确认的推导权限或跨部门用户数据缓存。

原子状态规则：登录、恢复、改密、退出和部门切换必须通过单一 action 更新 authStore 与
organizationStore。先递增 context revision 并取消旧请求/SSE，再清理旧缓存，最后提交新
上下文；响应提交前必须校验发起时的 revision，防止旧部门数据回灌。

## 八、安全技术指标

- 身份、权限、平台管理员和强制改密状态全部来自后端已验证响应。
- 前端源码、构建产物和测试 fixture 不硬编码 `admin/admin` 或真实生产凭据。
- 默认密码文案只说明规则，不在登录页向未认证用户展示具体账号密码组合。
- 密码字段使用 `type="password"`，显示按钮默认关闭并具备无障碍标签。
- 密码值不得发送到 console、Toast、遥测、错误平台、URL、localStorage 或 sessionStorage。
- 电话在列表、日志、测试截图中脱敏；真实个人数据不得用于自动化测试。
- 无部门平台管理员访问部门业务时，在路由渲染和数据请求两层停止；后端继续强制隔离。
- 权限未分配不能通过 `|| "viewer"`、默认角色或兼容适配器被提升。
- CSP、XSS 输出转义和依赖安全扫描沿用项目全局安全规范。
- 生产 source map 不得公开；上传错误平台前剥离源码中的环境变量和值，并设置访问控制。
- 禁止把完整 API 错误、请求/响应正文或 React 表单 state 传入遥测和错误边界。

## 九、测试技术栈与覆盖矩阵

### Vitest + Testing Library

- schema、格式化、脱敏、显示名、幂等键和错误适配器单元测试。
- authStore、organizationStore 的状态转换和缓存清理测试。
- 新增用户、个人设置、改密、用户菜单和路由守卫组件测试。
- MSW 如项目后续引入，可用于组件级 API mock；未引入前使用现有 fetch mock 约定。

### Playwright

- 真实浏览器下的登录、强制改密、刷新/直达路由和退出流程。
- 管理员创建、权限为空、默认密码提示、双击与断网重试。
- 平台管理员无部门负向访问和多任职切换。
- 改密后的旧令牌失效验证。
- Axe 扫描新增用户、个人设置和强制改密关键页面。

覆盖门槛：

- 用户整改相关语句覆盖率不低于 90%。
- 用户整改相关分支覆盖率不低于 85%。
- 身份、权限、部门隔离和密码流程每项至少包含一个正向与一个负向用例。
- P0/P1 E2E、并发和故障恢复测试失败时不得交付。

## 十一、不采用或暂缓的技术

- 不使用前端 RBAC 作为安全边界；按钮隐藏和路由守卫只改善交互。
- 不引入独立密码强度评分库；本期使用与后端策略一致的 Zod 校验，避免前后端结论不一。
- 不将用户创建做离线队列；账号创建必须获得后端确定结果。
- 不在浏览器保存一次性初始密码；受控密码交付方式由产品和后端另行确认。
- 不在本期增加 MFA、找回密码、用户批量导入和细粒度权限设计，它们属于需求文档的
  后续范围。

- [ ] 创建用户与改密表单使用统一校验和错误映射。
- [ ] 强制改密、平台级和部门级守卫已覆盖全部路由。
- [ ] 密码和个人信息不进入状态持久化、日志、遥测和测试产物。
- [ ] API client 支持幂等、请求取消、组织上下文和标准错误分类。
- [ ] 单元、组件、E2E、权限负向、并发、故障恢复和可访问性测试通过。
- [ ] CI 门禁、覆盖率和包体积预算生效。
- [ ] 后端真实接口联调通过，不依赖危险兼容默认值。

## 十三、浏览器、可访问性与交互基线

- 支持 Chrome、Edge、Firefox 最近两个稳定版本及 Safari 17+；关键路径不得依赖单一浏览器
  私有 API。`crypto.randomUUID` 等能力需要在支持矩阵内验证或提供无敏感数据的安全兼容实现。
- 布局验收覆盖 1366×768 和 1920×1080；表单缩放至 200% 时不丢失字段、错误和提交操作。
- 新增用户、强制改密、个人设置和用户菜单目标为 WCAG 2.1 AA：完整键盘访问、可见焦点、
  正确 label/description、错误摘要、状态播报、颜色对比度和焦点返回。
- 日期、电话号码和界面文案使用统一中文本地化规则；后端 error code 到中文文案采用集中映射，
  不在组件中散落字符串判断。

## 十四、构建、供应链与发布产物

- Node 生产/CI 版本固定为 22 LTS 的具体补丁版本，`npm ci` 必须基于提交的 lockfile；开发环境
  版本通过 `.nvmrc`、Volta 或等效机制统一。
- 生产构建注入应用版本和提交号，不把服务端密钥、默认密码或私有 URL 打包到前端。
- 依赖升级先通过类型、单元、组件、E2E、Axe、包体积和漏洞检查；禁止忽略高危漏洞直接发布。
- 发布归档至少包含构建校验值、lockfile、SBOM、许可证清单、构建日志、覆盖率、E2E、Axe、
  Bugbot、Security Review 和支持浏览器验收记录。
- 前端回滚必须与后端兼容窗口配套；V1 开关关闭后旧页面不得调用新写接口，新页面也不得
  静默调用旧角色接口。
