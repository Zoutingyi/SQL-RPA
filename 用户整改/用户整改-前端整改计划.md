# 用户整改——前端整改计划

最后更新：2026-08-25  
需求来源：[用户整改.md](用户整改.md)  
配套技术：[用户整改-前端技术栈清单.md](用户整改-前端技术栈清单.md)  
适用目录：`frontend/`

文档状态：**V1.0 商业交付实施基线**。页面完成不等于任务完成；真实接口联调、权限负向测试、
可访问性、可观测性、构建产物和上线证据缺一不可。

## 一、计划目标

本计划只拆解前端交付工作。账号、任职关系事务一致性、权限强制校验、密码哈希、
令牌失效、审计日志和数据隔离仍由后端负责，前端不得用按钮隐藏或路由跳转替代后端
安全控制。

前端交付目标：

- 管理员可以按完整字段创建用户，并为用户建立首个主职部门任职关系。
- 默认管理员允许在无部门上下文时进入平台管理功能，但不能进入部门业务页面。
- `must_change_password=true` 的用户只能进入强制改密流程或退出。
- 所有用户可查看只读个人资料，只能修改自己的登录密码。
- 左下角用户区展示姓名、当前任职，并提供个人设置、切换部门和退出入口。
- 敏感字段不进入日志、持久化存储、遥测或错误上报。

## 二、现状与差距

现有前端已经具备 React 路由、登录态、角色路由、部门树、主职/兼职任职列表、部门
切换和请求上下文注入，可复用这些基础设施。

仍需整改的主要差距：

- `AuthUser` 只有 `id`、`username`、`role` 等基础字段，缺少姓名、电话、平台管理员、
  强制改密和当前任职资料。
- 新增用户表单目前只有用户名、密码和角色，且强制要求至少 8 位密码；不符合
  “密码选填、默认 111111”和“权限允许为空”的要求。
- 用户角色仍被当作全局用户字段修改，需要改为账号资料与部门任职权限分离。
- 登录后没有强制改密路由守卫；无部门的平台管理员也会触发普通组织加载逻辑。
- 尚无 `/profile` 页面和修改密码 API 封装。
- 左下角只显示用户名、角色和退出按钮，缺少个人设置入口及完整的当前任职信息。
- 缺少用户创建幂等、密码流程和平台管理员无部门访问边界的自动化门禁。
- 当前 `src/api/auth.ts` 仍把 `role` 作为全局用户字段，`UserManagement.tsx` 仍直接修改
  全局角色；这是迁移对象，不得作为新接口兼容目标。
- 当前 `authStore.ts` 在登录后只写入租户/组织 ID，没有可靠保存 membership，并在
  `/api/auth/me` 失败时直接清除令牌；新登录状态机必须一次性提交完整上下文。
- 当前 `App.tsx` 只按是否登录和旧角色组织路由，没有强制改密、平台级/部门级分层与
  `/profile` 路由；全部属于 P0 阻断项。

外部前置条件：用户创建和任职展示依赖四级组织真实接口。`租户整改bugbot清单.md` 中组织
路由、上下文绑定、作用域和迁移 P1 未关闭前，前端不得通过 `departments.ts` 的旧 Tenant
兼容回退宣称联调完成；V1 页面开启后必须禁用这种静默回退。

## 四、分阶段整改任务

### P0：接口契约和身份模型

#### [~] UFE-00 固化 V1 契约与迁移开关

实施内容：

- 以 `用户整改-后端整改计划.md` 的 V1 固定接口契约和后端 OpenAPI 为唯一事实来源。
- 生成或校验 TypeScript DTO；禁止为缺失的 `membership_id`、`role`、`is_platform_admin`、
  `must_change_password` 设置 viewer/admin/默认部门等隐式值。
- 用户整改功能使用单一发布开关 `user_management_v1`；开关关闭时保留旧功能，开启时不得
  静默回退旧全局角色接口。生产切换必须由部署配置决定，不使用浏览器本地开关。
- 冻结错误结构 `{error: {code, message, field_errors, request_id}}`，组件只按 code 和字段
  错误分支，不解析 message 文本。
- 建立 OpenAPI 快照和前端契约检查，字段、状态码、空值或枚举漂移时 CI 失败。

技术指标：

- 用户 API DTO 使用 `any` 的数量为 0，危险默认角色和默认部门数量为 0。
- 新旧模式边界有自动化测试；V1 开启后发生 404/405 时不得回退旧用户接口。
- 契约快照与后端发布产物完全一致。

#### [~] UFE-01 扩展用户与任职类型

实施内容：

- 在 `src/api/auth.ts` 或独立 `src/types/user.ts` 中定义账号资料、当前任职、全部任职、
  权限状态和密码状态的类型。
- `AuthUser` 至少接收 `display_name`、`phone`、`is_active`、`is_platform_admin`、
  `must_change_password`、`password_changed_at` 和 `current_membership`。
- 部门、职位、主职/兼职、角色和权限放在 membership 类型中，不再从全局用户的
  `role` 推导所有业务权限。
- 对后端迁移期的缺失字段做显式兼容，不伪造电话、职位、任职或业务权限。

技术指标：

- TypeScript 严格编译通过，不使用 `any` 绕过用户和任职契约。
- 权限为空在前端保留为 `null` 或空集合，并统一显示“未分配”；不得回退为 viewer。
- `display_name` 为空时只回退到 `username`，不得用用户名覆盖并保存为姓名。

#### [~] UFE-02 完成管理员和个人 API 封装

实施内容：

- 补充用户列表、详情、创建、账号资料更新、任职更新和任职停用接口封装。
- 新增 `GET /api/auth/me` 完整资料解析和 `POST /api/auth/change-password`。
- 创建用户请求支持稳定 `Idempotency-Key`；同一次用户提交及其安全重试复用同一个键，
  表单内容改变或成功完成后才生成新键。
- 所有请求继续经过统一 API client，继承认证、部门上下文、取消和错误格式化能力。
- 后端返回已有创建结果时，前端展示该用户详情，不再次创建。

技术指标：

- 业务组件内直接调用裸 `fetch` 的数量为 0。
- 创建请求进行中重复提交数为 0；双击、回车连按和网络重试只产生一个逻辑操作。
- 409、401、403、422、429 和 5xx 均有可区分且不泄露敏感信息的用户提示。
- 首次创建返回 201，幂等重放返回 200 且识别 `Idempotent-Replayed: true`；同键不同请求
  收到 409 后停止自动重试。

### P0：登录、强制改密和访问边界

#### [~] UFE-03 改造登录状态机

实施内容：

- 登录成功后以 `/api/auth/me` 为准刷新用户、平台管理员、强制改密和当前任职状态。
- `must_change_password=true` 时进入强制改密状态，不初始化部门业务数据，不渲染普通
  主布局。
- 平台管理员无部门上下文时允许登录，不再错误提示“没有有效的部门任职”。
- 普通用户无有效任职且不是强制改密状态时，展示明确的不可用状态并允许退出。
- 退出、401 和改密后的会话切换统一清理账号令牌、部门上下文及组织作用域缓存。

技术指标：

- 登录成功后的身份判断只使用后端返回字段，前端不从用户名 `admin` 猜测管理员身份。
- 强制改密状态下普通业务 API 请求数为 0。
- 页面刷新、直接访问深层 URL 和浏览器前进后退均不能绕过强制改密。
- 登录成功后用户、令牌、organization、membership 和认证阶段必须原子提交；任何契约校验
  失败都清理全部认证及组织状态，不允许形成半登录状态。

#### [~] UFE-04 新增强制改密路由守卫

实施内容：

- 增加 `RequirePasswordChanged` 或等价守卫。
- 未改密用户只可进入 `/profile?section=password&forced=1` 和退出流程。
- 改密成功后使用后端返回的新令牌重新加载 `/api/auth/me`；若后端要求重新登录，
  清理本地会话并跳转登录页。
- 强制改密页面不提供关闭、跳过或返回业务首页入口。

技术指标：

- 对所有受保护路由执行参数化守卫测试，绕过成功数为 0。
- 改密成功后旧令牌访问受保护接口的 E2E 断言必须失败。
- 当前密码、新密码和确认密码不会写入 Zustand、localStorage、sessionStorage 或 URL。

#### [~] UFE-05 建立平台级与部门级路由边界

实施内容：

- 新增部门上下文守卫，覆盖会话、文档、数据库、审核、通知、用量和账单等部门业务。
- 平台管理员无部门时只展示用户管理、部门管理、系统设置和审计等平台入口。
- 需要部门的入口在无上下文时隐藏或禁用，并展示“请先切换部门”，不能发起跨部门
  聚合请求。
- 平台管理员切入合法部门后，权限以该 membership 和后端返回权限为准。

技术指标：

- 部门业务路由守卫覆盖率 100%。
- 无部门平台管理员进入任一部门业务 URL 时，业务数据请求数为 0。
- 部门切换继续执行请求取消、作用域缓存清理和页面数据重载。

### P1：管理员用户管理

#### [~] UFE-06 重构新增用户表单

实施内容：

- 表单包含登录账号、用户姓名、用户部门、职位、联系电话、登录密码和用户权限。
- 部门复用现有四级组织树，只展示后端返回的管理员可管理范围，禁用失效节点。
- 密码改为选填，明确标注“不填默认为 111111，并要求首次登录修改”。
- 权限允许为空，明确标注“未分配权限，仅可登录、查看个人设置和修改密码”。
- 客户端实施 trim、用户名字符、姓名、职位、电话和显式密码的即时校验；最终合法性
  仍以后端结果为准。
- 服务端字段错误映射到对应表单项，首个错误自动聚焦并提供可访问的错误摘要。

技术指标：

- 需求规定的 7 个字段展示率 100%，必填/选填文案与后端策略一致。
- 用户名提交前 trim；允许字符规则与后端共享契约测试一致。
- 表单校验错误不触发网络请求；提交中按钮和回车提交均被锁定。
- 键盘可完成全部表单操作，错误提示通过 `aria-describedby` 关联输入框。

#### [~] UFE-07 安全展示创建结果

实施内容：

- 创建成功后展示用户 ID、登录账号、姓名、部门、职位、权限状态和首次登录提示。
- 后端明确返回“使用默认密码”时，只提示默认密码交付状态；不得猜测或回显管理员
  输入的自定义密码。
- 一次性提示关闭或离开后不进入历史列表、通知、日志或持久化缓存。
- 幂等命中已有用户时复用同一结果页，并明确说明未重复创建。

技术指标：

- 密码值出现在 console、遥测、Toast、URL、localStorage 和 sessionStorage 的次数为 0。
- 创建成功后二次网络重放不会增加用户记录。
- 创建失败后表单保留非敏感字段，密码字段立即清空。

#### [~] UFE-08 重构用户列表与账号/任职编辑

实施内容：

- 列表展示登录账号、姓名、脱敏电话、主职部门、职位、权限状态、账号状态和资料完整度。
- 账号启停与姓名/电话更新使用用户接口；部门、职位和权限调整使用 membership 接口。
- 删除当前“直接修改全局 role”的交互；多任职用户进入详情后逐条展示和管理任职。
- 无管理权限用户不展示入口；403 时刷新当前身份和数据，避免保留失效操作按钮。
- 自己的账号启停、平台管理员降权等高风险动作遵循后端禁用结果和产品确认规则。

技术指标：

- 电话默认脱敏，完整值只在后端授权并由明确交互触发时展示。
- 用户账号字段与任职字段不存在交叉写入接口。
- 更新请求进行中对应行禁用，409 后自动刷新最新用户/任职状态。

### P1：个人设置和左下角用户入口

#### [~] UFE-09 新增 `/profile` 个人设置页面

实施内容：

- 页面可刷新、可直接访问，并展示账号、姓名、脱敏电话、当前部门、职位、主职/兼职、
  当前权限状态及全部只读任职列表。
- 缺失资料显示“资料待完善”，不得显示编造的占位数据。
- 密码只显示“已设置”或掩码，不渲染明文、哈希或可逆密文。
- 普通用户页面不提供修改姓名、电话、部门、职位、权限和主职状态的控件。
- 组织切换后重新读取当前用户资料，展示对应任职的职位和权限。

技术指标：

- 个人资料只读字段误编辑入口数为 0。
- URL 直接访问和刷新成功率 100%。
- 多任职切换后页面数据必须与当前 `membership_id` 一致，不允许显示上一个部门缓存。

#### [~] UFE-10 完成修改密码流程

实施内容：

- 独立表单包含当前密码、新密码、确认密码和显示/隐藏控制。
- 前端只执行必要的格式、一致性和默认弱密码校验，后端返回策略错误仍作为最终结果。
- 提交中禁用重复操作；失败后清空三个密码字段并聚焦当前密码。
- 成功后按冻结契约处理 `204 No Content`：清理账号令牌、组织上下文、SSE、活动请求和全部
  作用域缓存，跳转登录页并提示“密码已修改，请重新登录”。
- 对 401、422 和 429 提供统一且不泄露账号或密码内部状态的提示。

技术指标：

- 密码输入使用正确的 `autocomplete`：当前密码为 `current-password`，新密码为
  `new-password`。
- 密码字段离开组件或提交失败后从 React 状态清空。
- 密码内容进入日志、异常上下文、遥测或持久化存储的次数为 0。

#### [~] UFE-11 改造左下角用户菜单

实施内容：

- 主显示文本为 `display_name || username`。
- 展示当前部门路径、职位和主职/兼职；平台管理员无部门时显示“平台管理模式”。
- 提供个人设置、切换部门和退出登录入口；只有多个有效任职时启用部门切换。
- 菜单支持键盘、Escape 关闭、点击外部关闭和正确焦点返回。

技术指标：

- 姓名回退规则一致性 100%。
- 用户菜单通过键盘和屏幕阅读器基本操作检查。
- 强制改密期间只保留改密和退出入口。

### P2：质量、可观测性与交付门禁

#### [~] UFE-12 补齐自动化测试

单元测试：

- 用户名、电话、密码策略和权限空值的 schema/validator。
- 姓名回退、电话脱敏、权限“未分配”及 API 错误映射。
- 登录状态机、令牌清理和幂等键生命周期。

组件测试：

- 完整创建表单、重复提交保护、字段错误聚焦和一次性创建结果。
- 个人资料只读、改密表单、左下角用户菜单和部门切换后的刷新。
- 强制改密守卫、平台管理员无部门守卫及角色/权限负向用例。

E2E 测试：

- 管理员创建默认密码用户并完成首次登录改密。
- 非管理员无法看见入口，直接调用创建接口得到 403。
- 平台管理员无部门登录，只可访问平台页面；部门业务请求不会发出。
- 多任职切换后个人资料、职位和权限同步变化。
- 改密成功后旧令牌失效，新会话或重新登录可正常使用。
- 大小写重复用户名、并发重复提交、429、5xx 和断网恢复。

技术指标：

- 用户整改相关语句覆盖率不低于 90%，分支覆盖率不低于 85%。
- P0/P1 正向、权限负向和故障恢复 E2E 全部通过。
- 测试日志和失败截图不包含真实密码、完整电话或认证令牌。

- 对平台管理员无部门业务访问建立路由清单测试，新增业务路由必须显式归类为平台级

- Bugbot 与 Security Review 不存在用户创建、默认管理员、改密或部门越权相关 P1 问题。

#### [ ] UFE-14 可观测性与性能收口

实施内容：

- 记录不含个人信息的操作结果、错误类别、请求 ID 和耗时，不记录表单正文。
- 用户列表支持服务端分页、搜索与请求取消，避免一次加载全部用户。
- 个人设置和改密页面按路由懒加载；创建表单复用组织树缓存。

## 六、已冻结的前后端联调契约

- `/api/auth/login` 和 `/api/auth/me` 返回 `is_platform_admin`、`must_change_password`、完整
  用户摘要、当前任职和有效任职列表；无部门平台管理员的 organization 和 membership 为
  明确的 `null`，不得省略后由前端猜测。
- `POST /api/auth/users` 接收账号、姓名、organization ID、职位、电话、可选密码和可空角色；
  密码为空代表默认密码，角色为空代表未分配，前端不得替换为 viewer。
- 创建请求必须携带 `Idempotency-Key`：201 表示首次创建，200 加
  `Idempotent-Replayed: true` 表示安全重放，409 表示用户名冲突或同键请求摘要冲突。
- 用户列表服务端分页，默认 20、最大 100；电话默认由后端脱敏。账号更新与 membership
  更新分属不同接口，并携带 `version` 做乐观并发。
- `POST /api/auth/change-password` 成功固定返回 204，全部旧会话失效并要求重新登录。
- 强制改密期间只允许 login、me、change-password 和 logout；其他接口返回
  `403/PASSWORD_CHANGE_REQUIRED`。
- 错误固定为 `{error: {code, message, field_errors, request_id}}`。任何破坏性变更必须先更新
  OpenAPI 和两端契约测试，不接受口头约定或临时兼容分支。
