## 零、专业审阅结论与冻结决策

当前实现仍是旧用户模型：`backend/models/schemas.py::User` 仅含用户名、全局角色和状态，
`backend/api/auth.py` 的新增用户接口仅接收用户名、必填密码和全局角色，个人设置、强制改密、
令牌版本、平台管理员和事务化 OrganizationMembership 尚未形成闭环。因此本计划是开发任务，
不能依据“已有登录和用户列表页面”判定已完成。

为避免前后端继续等待确认，V1 冻结以下决策：

- 登录账号全局唯一，唯一性按 `trim + Unicode NFKC + casefold` 后的 `username_normalized` 判断；
  原始 `username` 只用于展示。用户名在 V1 仅允许 ASCII 字母、数字、`.`、`-`、`_`，长度 3～64。
- `User` 只保存登录身份和全局状态；部门、职位、主职/兼职和角色只保存在
  `OrganizationMembership`。旧 `User.role` 仅作迁移兼容，不得参与新业务授权。
- 新增用户的 `password` 缺省或空字符串时使用 `111111`，并设置
  `must_change_password=true`；显式密码不得为默认弱密码并执行服务端密码策略。
- 权限为空统一表示为 `role=null`（API）和 `role='unassigned'`（数据库兼容值）；不得回退为
  `viewer`。本期角色仍使用 `viewer/operator/approver/admin`，细粒度权限代码不在本期实现。
- 默认平台管理员账号和密码均为 `admin`，只在“数据库中不存在任何平台管理员”时初始化一次；
  生产环境允许环境变量覆盖。首次登录必须改密，改密后重启不得重置。
- 改密成功统一返回 `204 No Content`，递增 `token_version`，撤销该用户全部访问令牌和组织
  上下文令牌，并要求重新登录；前端不得依赖服务端返回新令牌。
- 平台管理员无部门登录时，`organization`、`current_membership` 均返回 `null`；平台令牌不能
  访问任何部门业务接口。选择合法任职后再签发组织上下文令牌。
- 所有写接口使用结构化错误和 `request_id`，不再以自由文本 `detail` 作为前端业务判断依据。

### V1 固定接口契约

`POST /api/auth/users` 请求字段固定为：

```json
{
  "username": "zhang.san",
  "display_name": "张三",
  "organization_id": "uuid",
  "job_title": "项目经理",
  "phone": "13800138000",
  "password": null,
  "role": null
}
```

- 必填：`username`、`display_name`、`organization_id`、`job_title`、`phone`。
- 选填：`password`、`role`；`null`、缺省和空字符串的密码均按默认密码处理，但响应中绝不
  返回密码值。
- 请求必须携带 `Idempotency-Key`。首次成功返回 `201`；同一操作者、同一键、同一请求摘要
  重放返回 `200` 并带 `Idempotent-Replayed: true`；同一键但摘要不同返回 `409`。
- 响应必须包含用户资料、主职任职、`used_default_password` 和 `must_change_password`，不得
  包含密码、哈希或可长期复用的密码提示。

其他固定接口：

- `POST /api/auth/login`：返回访问令牌、用户资料、`must_change_password`、
  `is_platform_admin`、当前任职和全部有效任职；平台管理员允许当前任职为 `null`。
- `GET /api/auth/me`：刷新后恢复身份的唯一事实来源，返回与登录响应一致的用户和任职摘要。
- `GET /api/auth/users?page=&page_size=&query=&status=`：服务端分页；默认 20、最大 100。
- `GET /api/auth/users/{user_id}`：返回账号资料和调用者可管理范围内的任职。
- `PATCH /api/auth/users/{user_id}`：仅允许姓名、电话、账号启停和 `version`，采用乐观并发。
- `POST /api/departments/{organization_id}/memberships`、
  `PATCH /api/departments/{organization_id}/memberships/{membership_id}`：只处理职位、角色、
  主职/兼职和任职状态，不修改全局账号字段。
- `POST /api/auth/change-password`：接收当前密码、新密码和确认密码，成功固定为 `204` 并使
  全部旧会话失效。

错误响应固定为：

```json
{
  "error": {
    "code": "USERNAME_ALREADY_EXISTS",
    "message": "请求无法完成",
    "field_errors": {"username": "账号已存在"},
    "request_id": "uuid"
  }
}
```

生产响应不得暴露目标用户或组织是否存在、堆栈、SQL、密码策略内部配置或其他租户数据。

## 一、执行原则

- `[ ]` 未开始；`[~]` 开发中；`[x]` 已完成；`[!]` 阻塞。
- 全局 User 只表示登录身份；部门、职位、角色和主职/兼职只保存在 OrganizationMembership。
- 用户与主职任职必须在同一数据库事务中创建，任何一步失败均整体回滚。
- 普通用户只允许修改自己的密码，不允许修改姓名、电话、部门、职位、角色或主职状态。
- 平台管理员没有组织上下文时，只能访问平台管理接口，不能读取任何部门业务数据。
- 密码、密码哈希和默认凭据不得进入日志、审计、通知、监控或普通 API 响应。
